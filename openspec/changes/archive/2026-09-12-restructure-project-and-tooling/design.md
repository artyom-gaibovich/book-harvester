## Context

Текущий код (см. `proposal.md` — Why) сосредоточен в `engine/IprBook.go`: авторизация по cookies, HTTP-запросы, разбор JSON API iprbookshop, потоковая AES-CBC расшифровка кадров и получение названия книги — всё в одном пакете `engine`. Точка входа `main.go` читает ID из stdin. Референс `user-service` даёт готовый шаблон слоистой архитектуры (`internal/{domain,repository,service,handler,config}` + `cmd/server`), набор линтеров (`golangci-lint` v2, `go-arch-lint`), Makefile, многоступенчатый Dockerfile и GitHub Actions. Проект — интерактивная CLI-утилита, а не HTTP-сервис, поэтому слои переносятся адаптированно.

Ограничения: без изменения протокола iprbookshop (эндпоинты, формат кадров, JWT `session_key`), без новых runtime-зависимостей, Go — из стандартной библиотеки. Правила проекта требуют кодов задач `IPRD-XXX` и запрещают деструктивные git-операции без явного разрешения.

## Goals / Non-Goals

**Goals:**

- Разнести fat-файл на изолированные слои с проверяемыми границами (`go-arch-lint`).
- Идиоматичные Go-имена пакетов и файлов (строчные, без CamelCase-файлов).
- Единый источник конфигурации — `.env`/окружение (`COOKIE`, `DOWNLOAD_DIR`).
- Детерминированная раскладка загрузок: `downloads/<timestamp>_<slug>/<name>.pdf`.
- Полный инструментарий: Makefile, линтеры, Dockerfile, docker-compose, CI-workflow.

**Non-Goals:**

- Изменение сетевого протокола, формата токена или алгоритма расшифровки.
- Ввод флагов/подкоманд CLI сверх текущего stdin-ввода ID (можно позже).
- Тестовое покрытие «под ключ» — вводятся точки для тестов, но 100% покрытие не цель.
- Публикация Docker-образа в реестр.

## Decisions

### Раскладка пакетов

Выбрана адаптированная слоистая структура вместо дословного копирования `user-service`:

- `internal/domain` — типы предметной области (`Book`, `DumpResult`) и sentinel-ошибки; без внешних зависимостей.
- `internal/config` — загрузка `.env` и окружения по образцу `user-service/internal/config` (функции-опции, `FromEnv`), поля `Cookie`, `DownloadDir`.
- `internal/downloader` — HTTP-клиент с cookies, получение токена/названия, скачивание потока (роль «repository» — работа с внешним источником).
- `internal/decrypt` — потоковая AES-CBC расшифровка кадров в PDF (чистая функция, легко тестируется).
- `internal/storage` — формирование пути `<timestamp>_<slug>`, транслитерация названия, запись файла.
- `internal/app` (или `service`) — оркестрация: для каждого ID вызвать downloader → decrypt → storage.
- `cmd/dumper` — точка входа: чтение stdin, сбор конфигурации, вызов оркестратора, вывод.

Альтернатива — дословные `repository/service/handler` из `user-service` — отклонена: `handler` осмыслен для HTTP, для CLI слой ввода естественнее держать в `cmd`. `go-arch-lint.yml` описывает именно эти компоненты и их разрешённые зависимости (`cmd` → всё; слои → `domain`).

### Транслитерация slug

Название книги (кириллица) → латиница по таблице транслитерации → нижний регистр → недопустимые символы и пробелы в `-`. Своя маленькая таблица в `internal/storage` без внешних зависимостей. Альтернатива — библиотека транслитерации — отклонена ради Non-Goal «без новых зависимостей». При пустом/недоступном названии slug = ID книги (см. спеку).

### Конфигурация через .env

Переносится подход `user-service`: собственный парсер `.env` в `internal/config` (без `godotenv`), приоритет — реальное окружение над файлом. Переменная `COOKIE` заменяет `IPR_COOKIES`/`cookies.txt`. Это BREAKING — фиксируется в README и `.env.example`.

### Инструментарий

`Makefile`, `.golangci.yml`, `.go-arch-lint.yml`, `Dockerfile`, `.dockerignore`, workflow-файлы адаптируются из `user-service` заменой имён (`user-service` → `iprbooks-dumper`, `cmd/server` → `cmd/dumper`) и снятием HTTP-специфики (`EXPOSE`/порт не нужны). `docker-compose.yml` добавляется под интерактивный запуск с монтированием `downloads/` и передачей `COOKIE`; так как CLI читает stdin, сервис описывается с `stdin_open`/`tty`.

### История git

Squash-переписывание `master` в осмысленные коммиты с кодами `IPRD-XXX` (тематические группы: инфраструктура/тулинг, реструктуризация кода, конфигурация, документация). Выполняется через `git rebase`/`reset`+пересборку коммитов и `push --force`. Это деструктивно и требует явного разрешения на этапе apply — план фиксирует порядок, но не выполняет его без подтверждения.

## Risks / Trade-offs

- **Переписывание опубликованной истории (force-push) необратимо и ломает клоны** → выполнять только по явному разрешению; предварительно сделать резервную ветку/тег текущего `master`.
- **BREAKING смена конфигурации cookies** ломает существующий сценарий пользователя (`cookies.txt`) → README и `.env.example` явно документируют переход; сообщение об ошибке подсказывает задать `COOKIE`.
- **Транслитерация несовершенна** (спорные буквы, коллизии slug) → префикс-timestamp делает имена уникальными даже при одинаковом slug; при пустом названии — fallback на ID.
- **go-arch-lint/golangci-lint версии** могут расходиться с окружением → версии закреплены в Makefile (`install-tools`) и workflow, как в `user-service`.
- **Docker для интерактивного CLI** неудобен (нужен stdin) → compose помечается `stdin_open: true`/`tty: true`; в README отмечается, что основной сценарий — локальный запуск `go run`/`make run`.

## Migration Plan

1. Создать резервный тег/ветку текущего `master` перед любым переписыванием истории.
2. Ввести новую структуру и тулинг, удалить мусор, перенастроить конфигурацию (обычные коммиты).
3. Только после подтверждения пользователем — squash-переписывание истории и `push --force`.
4. Откат: восстановление из резервного тега/ветки (шаг 1).
